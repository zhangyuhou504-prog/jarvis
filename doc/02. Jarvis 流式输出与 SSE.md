# 02. Jarvis 流式输出与 SSE

## 1. 阶段目标

为 Jarvis 实现 AI 流式对话能力，使模型生成内容能够逐段返回客户端，同时在服务端收集完整回答，为后续对话持久化和 Memory 功能做准备。

## 2. 技术方案

本阶段采用：

- Java 21
- Spring Boot
- Spring WebFlux WebClient
- Reactor Flux
- Server-Sent Events（SSE）
- OpenAI 兼容 Chat Completions API

本阶段直接使用 WebClient 对接模型网关，而不是通过 Spring AI ChatClient 实现流式调用。

## 3. 核心概念

### 3.1 Token

大语言模型处理文本的基本单位。一个汉字不一定对应一个 Token，一个 Token 也不一定对应一个完整汉字。

### 3.2 Chunk

一次产生或传输的一段数据。模型生成的文本可以分多次传递，每次传递的数据就是一个数据块。

Chunk 不等于 Token，也不一定等于一次网络读取的数据。

### 3.3 Flux

Reactor 提供的响应式数据流类型，可以持续产生多个数据元素。

本项目使用 `Flux<String>` 表示持续产生的文本内容。

### 3.4 SSE

Server-Sent Events，基于 HTTP 的服务端事件推送机制。

本项目通过 SSE 将模型生成的内容逐步返回客户端。

## 5. 模型请求构建

通过 OpenAI 兼容协议构建请求：

- `model`：指定模型。
- `stream`：设置为 true，开启流式输出。
- `messages`：包含 System Prompt 和 User Prompt。

核心请求结构：

```json
{
  "model": "configured-model",
  "stream": true,
  "messages": [
    {
      "role": "system",
      "content": "System Prompt"
    },
    {
      "role": "user",
      "content": "User Message"
    }
  ]
}
```

项目使用 `LinkedHashMap` 构建请求参数，并通过 WebClient POST 到 `/chat/completions`。

## 6. SSE 数据解析

模型返回的数据通常包含：

```json
{
  "choices": [
    {
      "delta": {
        "content": "你好"
      }
    }
  ]
}
```

项目通过 Jackson `JsonNode` 解析 JSON，提取：

```java
choices.get(0)
       .path("delta")
       .path("content")
       .asText("");
```

同时处理 `[DONE]` 结束标志和无文本事件。

## 7. 完整答案收集

流式输出期间，使用 `StringBuilder` 收集每个 Chunk：

```java
StringBuilder fullAnswer = new StringBuilder();

.doOnNext(fullAnswer::append)
```

这里采用旁路收集：

- 原始数据流继续向下游传递。
- `doOnNext` 同时将内容追加到完整答案。
- 不需要额外订阅一次 Flux。

同一订阅内的 `onNext` 回调按序执行，因此当前实现不需要为 StringBuilder 加锁。

注意：StringBuilder 在方法调用时创建。如果未来需要重复订阅同一个 Flux，应考虑使用 `Flux.defer()` 为每次订阅创建独立状态。

## 8. 异常和生命周期处理

当前实现使用以下 Reactor 操作符：

| 操作符 | 作用 |
|---|---|
| `doOnNext` | 接收数据时执行旁路逻辑 |
| `timeout` | 限制等待下一个数据元素的时间 |
| `doOnError` | 记录流中异常 |
| `onErrorResume` | 将异常恢复为友好提示 |
| `doOnComplete` | 正常完成时执行收尾 |
| `doFinally` | 在完成、异常或取消时执行最终逻辑 |

当前通过 `AtomicBoolean` 标记是否发生异常。

注意：`onErrorResume` 会将错误转换为备用数据流，因此下游可能收到 `onComplete`。此时 `doFinally` 的信号可能是 `ON_COMPLETE`，不能仅依赖它判断上游是否曾发生异常。

另外，`[DONE]` 是模型协议中的结束标志，不等于 Reactor 的 `onComplete`。

## 9. 重要设计认识

### 9.1 实时推送和完整答案收集

两者可以在同一次订阅中完成，不需要重复调用模型接口。

### 9.2 SSE 和 Chunk 的区别

Chunk 是数据片段，SSE 是传输事件协议。

客户端不能认为每次网络读取都对应一条完整 SSE 消息。

### 9.3 客户端断开连接

客户端取消订阅后，Reactor 的取消信号可以向上游传播，使 WebClient 尽可能取消正在进行的请求。
